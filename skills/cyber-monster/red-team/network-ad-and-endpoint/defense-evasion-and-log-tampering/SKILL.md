# Defense Evasion and Log Tampering - Red Team Sub-Skill

> **Cyber Monster** | Family: [`Network, Active Directory and Endpoint`](../README.md) | Tier: **core** | Paired Counterpart: [`identity-and-authentication-monitoring`](../../../blue-team/detection-and-monitoring/identity-and-authentication-monitoring/SKILL.md)

## Mechanism and Preconditions

Log tampering is an integrity attack on the evidence itself, and it takes three forms: suppressing new events (stopping or patching the logging service), deleting existing events (clearing a channel or editing an EVTX file), and disabling the policy that produces events (turning off audit subcategories). Each leaves a different trace, and the trace is the residual signal: a clearing event, an audit policy change event, or a gap in a monotonic record sequence.

- **CWE-693 (Protection Mechanism Failure):** The product does not use or incorrectly uses a protection mechanism that provides sufficient defense against directed attacks against the product.

## Quick Start

Follow these **IF / THEN** decision rules before reading any companion file:

1. **IF** a channel was cleared **THEN** Security 1102 or System 104 records it, unless the clearing method bypassed the API
2. **IF** audit policy was changed **THEN** event 4719 records the change with the subcategory and the new setting
3. **IF** the logging service was stopped or patched **THEN** event 1100 and the absence of any subsequent events are the evidence
4. **IF** the EVTX file itself was modified **THEN** header and record checksums and `EventRecordID` continuity are the only reliable checks
5. **IF** the question is *detect, hunt, contain or harden* rather than *prove and scope* **THEN** pivot to the paired Blue skill [`identity-and-authentication-monitoring`](../../../blue-team/detection-and-monitoring/identity-and-authentication-monitoring/SKILL.md) and keep this file for attack-path evidence only
6. **IF** required preconditions for `defense-evasion-and-log-tampering` are absent after inspecting the evidence **THEN** **STOP** and classify the pattern as a verified non-finding rather than forcing a fit

## Procedure

1. **Establish the log's expected continuity.** Record the current `EventRecordID` high-water mark, the channel's maximum size and its retention policy. Continuity in `EventRecordID` is the only property a clearing tool cannot easily fake, so it is the primary check.
2. **Read the events that record tampering itself.** Security 1102 for a cleared audit log, System 104 for a cleared system log, 1100 for the logging service stopping, 4719 for an audit policy change, and 4906 or 4912 for policy changes on newer builds. These events are generated by the logging service, so a suppression attempt that stops the service produces none of them.
3. **Compare channel record counts against a peer group.** A host with materially fewer records than peers of the same role for the same window is the anomaly. This works even when the tampering left no explicit event.
4. **Name the stop condition.** Stop at the first proven integrity break: a clearing event, a non-monotonic record id, or a peer-relative gap. Reconstructing what was deleted is a forensic exercise, not an assessment one.
5. **State the proof.** Proof is the specific event id with its timestamp, or the record-id discontinuity, or the peer comparison for a fixed window. A suspicion that logs were altered without one of those is not a finding.

## Concrete Patterns

| Indicator / API / Artifact | Analytical Role |
|---|---|
| Security 1102 for an audit log cleared | Proves the audit channel was cleared through the API, which the logging service records; Windows. |
| System 104 for a log cleared | Proves a non-security channel was cleared; Windows. |
| Security 4719 for an audit policy change | Proves an audit subcategory was changed, with the new value in the event; Windows. |
| Non-monotonic `EventRecordID` or a checksum mismatch | Proves direct file modification, which bypasses the API and therefore leaves no clearing event; Windows EVTX files. |
| Security 1100 for the logging service stopping | Proves logging was halted, which is the strongest suppression signal when followed by silence; Windows. |

## Worked Contrast

**Weak configuration — audit policy minimal, log size small, and no central forwarding:**

```powershell
auditpol /get /category:*
# only 'Logon' is enabled, the Security channel is 20 MB with overwrite-as-needed,
# and no subscription forwards events off-host
```

**Hardened configuration — audit subcategories enabled, channel sized for retention, events forwarded:**

```powershell
auditpol /set /subcategory:'Process Creation' /success:enable /failure:enable
auditpol /set /subcategory:'Audit Policy Change' /success:enable
wevtutil sl Security /ms:1073741824
# and configure a Windows Event Forwarding subscription to the collector
# verification: the subcategory reads Enabled and events appear on the collector
```

**Why this matters:** tampering only matters where the evidence is local and thin, so the controls are audit coverage, retention and forwarding, verified by events arriving at the collector.

## When It Is NOT This Issue

- **A 1102 event during a sanctioned maintenance window.** Administrators clear logs; correlate with the change record and the acting account.
- **A record-count difference caused by retention rotation.** A channel at its maximum size overwrites the oldest events, which looks like a gap; check the file size and the retention policy.
- **A 4719 for a documented audit baseline rollout.** Policy changes are normal during hardening; confirm the source is the configuration management system.
