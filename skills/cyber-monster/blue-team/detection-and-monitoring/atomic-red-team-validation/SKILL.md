# Atomic Red Team Validation - Blue Team Sub-Skill

> **Cyber Monster** | Family: [`Detection and Monitoring`](../README.md) | Tier: **core** | Paired Counterpart: [`adversary-emulation-planning`](../../../red-team/osint-and-red-operations/adversary-emulation-planning/SKILL.md)

## Mechanism and Preconditions

An atomic test is a technique-shaped probe whose only purpose is to make a specific sensor emit the artifact your rule claims to read. That makes validation a two-outcome measurement, not a one-outcome one: the rule must fire *and* the raw event must exist in the pipeline, in the same window, carrying the fields the rule reads. Those two outcomes fail independently and the failure modes are different — a fired alert with no raw event underneath means the rule fired on something else (a co-occurring signal, a cached match, a fixture replay), while a raw event with no alert means the rule's selection, field mapping, or backend compilation does not reach that artifact. Atomic tests are also deliberately host-local and reversible: each test carries `prereqs`, an `executor`, and a `cleanup_command`, so the discipline is to prove prereqs first, bound the execution with an explicit timeout, capture the sensor output during the run rather than after, and run cleanup in the same session. Validation value collapses when the test is run without prereq confirmation (it silently no-ops and "proves" nothing) or without cleanup (the artifact persists and contaminates every later hunt on that host).

- **CWE-778 (Insufficient Logging):** When a security-critical event occurs, the product either does not record the event or omits important details about the event when logging it.

## Quick Start

Follow these **IF / THEN** decision rules before reading any companion file:

1. **IF** the technique has no corresponding atomic, or the atomic exists but its executor is unavailable on the target OS **THEN** stop and report `Inconclusive (No Emulation Path)`; do not substitute a different technique's test and present it as coverage.
2. **IF** `Invoke-AtomicTest <technique> -TestNumbers <n> -CheckPrereqs` reports an unsatisfied prerequisite **THEN** resolve it with `-GetPrereqs` on an isolated host only; **IF** it still fails **THEN** classify `Inconclusive (Prerequisite Unmet)` — an atomic that skips prerequisites executes nothing and validates nothing.
3. **IF** the sensor is EDR with its own alert layer **THEN** validate against the EDR alert stream and the raw event stream separately; **IF** the sensor is a forwarded Windows event channel **THEN** validate at the index, because the channel can hold the event while the forwarder or parser drops it.
4. **IF** the rule is a Sigma rule **THEN** validate the *compiled* backend query, not the YAML, since modifier and pipeline handling decide what actually runs; **IF** the rule is native SPL or KQL **THEN** validate the saved search as deployed, including its schedule and lookback.
5. **IF** the raw artifact appears in the window but the alert does not **THEN** the finding is `Control Gap (Rule or Mapping)` and the gap localises to selection, field name, or conversion — not to the sensor.
6. **IF** the alert appears but no raw artifact can be found for the same principal and host **THEN** the finding is `Control Gap (Match Provenance)`; re-check whether the alert was generated by a replay, a backfill, or a different event that happens to satisfy the condition.
7. **IF** telemetry source covering the technique's artifact is missing, disabled, or uncollected **THEN** report `INCONCLUSIVE (Telemetry Gap)` — NEVER report `Clean/Benign`.
8. **IF** you need the underlying offensive mechanics or audit preconditions **THEN** pivot directly to paired Red skill [`adversary-emulation-planning`](../../../red-team/osint-and-red-operations/adversary-emulation-planning/SKILL.md).

## Procedure

1. **Fix the claim before running anything.** Write the sentence the test must make true — technique, sensor, artifact field, expected rule identifier — and record it. A validation without a stated claim degenerates into "something appeared in the console".
2. **Confirm the prerequisite state on the target host.** Enumerate the test's `prereqs` and satisfy them inside the isolated range, never on production. Record the prereq result next to the test number; an unmet prereq is a definitive `Inconclusive`, not a soft pass.
3. **Snapshot the sensor's pre-state.** Capture the host's current event volume for the technique's channel, the agent's last-checkin time, and any pending policy change. A sensor that has been silent for hours will not report the probe either, and you must be able to tell those apart.
4. **Execute with a bounded timeout and an explicit test-number selection.** Run the single atomic rather than the whole technique folder. Unbounded execution turns a five-second probe into an interactive session that leaves artifacts you did not plan for.
5. **Harvest inside the run window, not after.** Query the raw artifact by host, principal, and the fields the rule reads, using a window that brackets the execution with margin for ingestion delay. Then query the alert stream for the same identity and window.
6. **Reconcile the two harvests into a verdict class.** Alert plus artifact is `Validated`. Artifact without alert is `Control Gap (Rule)`. Alert without artifact is `Control Gap (Provenance)`. Neither is `Inconclusive (Sensor)` when the pre-state check showed the sensor was healthy.
7. **Name the stop condition.** Stop and declare `Inconclusive` when the prereq state cannot be satisfied, when the sensor's pre-state check shows a coverage gap that predates the test, when ingestion delay exceeds the harvest window, or when the rule under test was modified inside the validation window and the deployed version is unknown.
8. **Run cleanup in the same session and verify it.** Cleanup is part of the test: a scheduled task, a service, a registry value, or a dropped binary left behind becomes a permanent false positive for every analyst afterwards and a contamination for the next validation.
9. **State what counts as proof.** Proof is one raw event in the pipeline, timestamped inside the run window, on the target host, for the target principal, plus one alert referencing the same host and principal, plus a cleanup verification that the artifact is gone. A screenshot of an alert without the event underneath is a claim about the rule's trigger, not about its data.

## Concrete Patterns

| Indicator / Artifact | Query class | What it proves |
|---|---|---|
| Raw event for the technique's channel inside the run window, filtered by host and executing principal | artifact harvest | The sensor and the pipeline delivered the artifact at all; without this row no later alert claim is meaningful |
| Alert record for the expected rule identifier matching the harvest host and principal | alert correlation | That this rule — not a neighbouring analytic — fired, which a bare alert count cannot show |
| Event count for the channel in the 30 minutes before and after execution | pre/post differential | Whether the artifact is attributable to the probe or is background noise the channel always carries |
| Sysmon EventID 25 or EventID 29 rows from the probe host | artifact-specific | For tamper and executable-write techniques, that the specific high-value event exists on this build rather than assuming the sensor version emits it |
| Sigma rule compiled output replayed against the harvested event as a fixture | conversion check | That the deployed backend query selects the artifact; a YAML rule can be correct and its compiled form wrong |
| Post-cleanup query for the artifact (task, service, registry key, dropped file) | cleanup verification | That the test left no residue; residue silently becomes the next exercise's false positive |

## Worked Contrast

**Weak / Noisy Detection Practice:**

```powershell
# Runs every atomic for a technique and calls the result a validation.
Invoke-AtomicTest T1053.005
# No prereq check, no timeout, no harvest window, no cleanup verification.
# Half the tests no-op on unmet prereqs and report success anyway;
# scheduled tasks remain registered and fire during every later hunt.
```

**High-Signal Grounded Artifact:**

```powershell
$Test = 2
Invoke-AtomicTest T1053.005 -TestNumbers $Test -CheckPrereqs
$Start = (Get-Date).ToUniversalTime().AddMinutes(-5)
Invoke-AtomicTest T1053.005 -TestNumbers $Test -TimeoutSeconds 120
# Harvest while the artifact is fresh, keyed to this host and the executing principal.
$Harvest = $Start
"SCHEDULED_TASK_WINDOW=$($Harvest.ToString('o')) test=$Test host=$env:COMPUTERNAME"
Invoke-AtomicTest T1053.005 -TestNumbers $Test -Cleanup
# Cleanup is verified, not assumed: re-enumerate tasks created inside the run window.
Get-ScheduledTask | Where-Object { $_.Date -gt $Harvest } | Select-Object TaskName, TaskPath
```

**Why this matters:** the strong form proves one stated claim with a prereq gate, a bounded run, a harvest keyed to the host and principal, and a verified cleanup; the weak form runs an unbounded batch, lets prereq no-ops count as passes, and leaves artifacts that will be mistaken for adversary activity later.

## When It Is NOT This Issue

- **Prereq no-op reported as a pass:** an atomic whose `prereqs` are unmet exits successfully without executing the payload, so the rule "not firing" says nothing about the rule. Only `-CheckPrereqs` output distinguishes this from a real negative.
- **Ingestion delay longer than the harvest window:** forwarded Windows channels batch, so the artifact can land after the query closes. The apparent gap is transport latency, not a rule defect; re-query by the event's own timestamp with a widened window before recording a gap.
- **Sensor policy pushed between pre-state and execution:** a configuration management run that narrows Sysmon filtering or disables a channel mid-test produces exactly the signature of a broken rule. Compare the agent policy version across the run.
- **Rule changed mid-window:** a rule edited or recompiled during the validation invalidates the outcome, because alert and artifact are then judged against different logic. Pin the deployment hash before the run and re-read it after.
- **Leftover artifact from a previous exercise:** a scheduled task or service from an earlier test satisfies the rule and is mistaken for the current probe's confirmation. Enumerate pre-existing artifacts before execution, not only after.

## Anti-Hallucination Ban List

- **NEVER fabricate CVE identifiers, CVSS vector strings, or vendor advisory URLs** — you MAY cite standard CWE/OWASP/ATT&CK IDs when accurate, but cite specific CVEs only from user input or `CASES.md`.
- **NEVER conclude a host or tenant is 'clean' when telemetry covering the tested artifact was disabled, rotated out, or uncollected.**
- **NEVER report a detection as validated on the strength of an alert alone, without the raw event that the rule claims to read.**
- **NEVER recommend destructive containment (wiping disks, deleting accounts, or isolating domain controllers) before preserving volatile evidence and checking blast radius.**

## Preconditions Checklist

Verify all five checks before emitting your final output:

- [ ] **Evidence source confirmed:** the sensor, channel, index, and agent policy version that must carry the artifact were enumerated on the target host before execution, and the pre-state volume was captured.
- [ ] **Differential defined:** channel volume before and after execution, plus the harvest window, were recorded so the artifact is attributable to the probe rather than to background traffic.
- [ ] **Stop condition stated:** unmet prereq, sensor gap predating the test, ingestion delay beyond the window, or an unknown deployed rule version is named as the reason for `Inconclusive`.
- [ ] **Proof standard met:** one raw event inside the window on the target host and principal, one alert for the expected rule identifier on the same identity, and a verified cleanup; all three, or the verdict is downgraded.
- [ ] **Output Contract followed:** Response uses the exact headings in *Strict Output Contract* below.

## Operating Notes

- **One claim per run:** validate a single rule against a single test number, and record the pair. Batch validation produces a pass rate nobody can reproduce or defend.
- **Taxonomy framing:** Keep framework references concise (parent CWE/ATT&CK categories `CWE-778`); note that ATT&CK v18 replaced per-technique detections with detection strategies and analytics, so a validated rule should name the analytic it satisfies rather than a bare technique ID.
- **Safety & authorization:** Execute only inside an authorized, isolated range with a documented change window; the probe is host-local and reversible, cleanup is mandatory, and no test is run against a production control plane.
